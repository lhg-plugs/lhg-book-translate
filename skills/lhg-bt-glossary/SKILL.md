# lhg-bt-glossary：术语表锁定

> 目标：开译前回答"全书的关键词到底叫什么"。
> 核心纪律：**术语表没锁定不开译**。90% 的译文返工来自术语前后不一，而不是语言功底。

## 1. 何时使用

- 接到一本新书/新文档的翻译任务，还没动笔时 → 必须先跑本 skill
- 翻译进行到一半发现术语混乱（同一词三种译法）时 → 停下来，跑本 skill 重建术语表，已译章节按新表统一替换
- 用户只想校对已有译文、不做新翻译时 → 跳过本 skill，直接用 lhg-bt-audit

## 2. 输入与输出

- **输入**：原文目录（`source/` 下的章节文件）+ 领域说明（如"AI 科普"/"历史小说"，可空）
- **输出**：`glossary.md`，表头固定为 `| 原文 | 统一译法 | 禁用译法 | 备注 |`，顶部标注 `状态：已锁定（YYYY-MM-DD）`

## 3. 第一步：通读抽术语（四类）

不要只看目录就定术语表——必须通读全文（至少快速通读一遍），按以下四类抽取候选，每个候选记录出现次数：

1. **专有名词**：人名、地名、机构名、书名、产品名。如 "Gradient Descent"、"ImageNet"。
2. **核心概念**：全书反复出现的关键概念，往往是作者自创或领域黑话。如 "emergent behavior"。
3. **技术缩写**：API、GPU、LLM 等。缩写必须在"备注"列写明首次出现规则："首次出现用全称+缩写，如'应用程序接口（API）'，后文可用缩写"。
4. **高频短语**：反复出现的关键动词/短语组合，译法不统一最容易穿帮。如 "in practice"、"trade-off"。

抽取技巧：用文本搜索统计词频——出现 3 次以上的名词短语默认进候选；只出现 1 次的专有名词也要进（人名地名错一次就是事故）。

## 4. 第二步：定译名（每个术语 2-3 个候选）

对每个候选术语给出 2-3 个译名，标注推荐项与理由。定译名的优先级：

1. **行业惯例优先**：该领域中文出版物/教材通用什么译法就用什么（如 "machine learning" → "机器学习"，不许自创"机械学习"）。
2. **读者认知优先**：有多个惯用译法时，选目标读者最熟悉的那个，并在"备注"列记下备选。
3. **全书统一优先**：一个术语只许一个译法；"禁用译法"列写下所有见过的错误/别扭译法，方便审计脚本自动拦截。

**诚实原则**：拿不准的术语不要猜——查该领域的中文教材、百科、已出版译著；查不到就标 `[待确认]` 交给用户，不许编一个"听起来对的"译名。

## 5. 第三步：用户拍板与锁定

1. 把候选清单（含译名选项与推荐理由）交给用户确认；有分歧的术语单独拎出来讨论，不许跳过。
2. 用户确认后写入 `glossary.md`，顶部写 `状态：已锁定（YYYY-MM-DD）`。
3. 输出确认清单：术语总数、锁定日期、`[待确认]` 术语清单（如有）。

锁定后的修改规则：**改一个译名 = 全书统一替换 + 更新锁定日期**。不许只改当前章节——术语表是全书的，不是单章的。

## 6. 第四步：翻译中的术语维护

- 翻译中遇到表外术语：先登记为 `[待确认]`、按临时译法翻，并在 `translation-log.md` 记一笔；用户确认后转正进表。
- 每周（或每 5 章）做一次术语表复核：新增术语有没有进表？有没有人偷偷用了禁用译法？（跑 `translation_audit.py` 的术语 3 条规则自动查）

## 7. 反模式（这些做法一定翻车）

- **边翻边定**：第一章叫"机器学习"，第五章叫"机械学习"，第十章又叫"机器学习法"——读者会以为是三个东西。
- **术语表只存脑子里**：不写下来就等于没有，多人协作/跨会话必崩。
- **缩写裸奔**：正文第一次出现 "LLM" 不给中文全称，读者直接弃读。
- **锁定后偷改**：某章觉得"神经网络"不好听改成"类脑网络"，还不更新术语表——审计脚本就是抓这个的。
- **过度收录**：把只出现一次的普通词也塞进术语表，表膨胀到 500 条就没人看了。门槛：专有名词全收，普通概念出现 3 次以上才收。

## 8. 自检与反馈

质检门（术语表交付前自查）：

- [ ] 四类术语全覆盖（专有名词/核心概念/缩写/高频短语）
- [ ] 每个术语有且仅有一个统一译法，禁用译法列非空（至少写"无"）
- [ ] 缩写类术语的"备注"列写明了首次出现规则
- [ ] 顶部有锁定状态与日期
- [ ] `[待确认]` 术语单独成表，用户已知晓

标准冒烟用例：用本仓库 `fixtures/trans-good/glossary.md` 为参照——表头四列齐全、锁定状态明确、无 `[待确认]` 残留。

发现 bug 或有改进建议，以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-book-translate/issues，正文写清"复现步骤 → 实际表现 → 期望表现"。

## 9. 附：术语命名实战例库

### 9.1 科技类
- machine learning → **机器学习**（禁用：机械学习、机器学习法）。理由：全国科学技术名词审定委员会审定译名，教材通用。
- neural network → **神经网络**（禁用：类神经网络、人工神经网）。理由：约定俗成，"人工"二字在上下文明确时可省。
- overfitting → **过拟合**（禁用：过度拟合、过适应）。理由：短、准，学术界通用。

### 9.2 缩写类（备注列写法示例）
- API → 应用程序接口，备注：`首次出现写"应用程序接口（API）"，后文可用 API`
- LLM → 大语言模型，备注：`首次出现写"大语言模型（LLM）"；面向大众的书建议全书用中文`

### 9.3 人文类
- 人名：音译优先，查《世界人名翻译大辞典》；已有惯用译名（如"亚当·斯密"）不许自创新译。
- 书名：查已有中译本，用通行译名；无中译本时直译+原文括号备注。

### 9.4 自创概念（作者造的词）
- 先看作者自己有没有给定义：有定义→按定义意译；无定义→音译+原文备注。
- 自创概念的译名必须在"备注"列写清决策依据，方便后人接手。

## 10. 附：术语表评审 FAQ

**Q：术语表多少条合适？**
A：一本 20 万字的书，术语表通常在 80-200 条。超过 300 条说明收录标准太松，回头按"出现 3 次以上"过滤一遍。

**Q：中英双语术语表还是纯中文？**
A：必须双语对照（原文列不可少）。纯中文术语表在跨章节核对时无法定位原文，是半成品。

**Q：术语表要不要给读者看？**
A：建议作为附录/前言的一部分出版。读者拿着术语表读，体验好很多；这也是专业译著的标配。

**Q：小说类书的术语（人名/地名）怎么定？**
A：人名地名一旦确定，全书不许改——小说读者对名字最敏感。建议单独建"人名地名表"，与概念术语表分开维护。

## 11. 附：术语表维护工作流（翻译进行中）

翻译开工后，术语表是活文档。推荐工作流：

1. **登记**：译者每章把新术语记进 `translation-log.md`，格式 `新术语：原文 → 临时译法（待确认）`。
2. **确认**：每 3 章开一次术语评审（15 分钟）：过一遍待确认清单，用户拍板。
3. **转正**：确认的术语进 `glossary.md`，更新锁定日期；临时译法全书统一替换。
4. **复核**：跑审计脚本 BT-TERM 三条规则，确认无残留、无禁用译法。

## 12. 附：多人协作规范

- 术语表由**一个人**维护（术语总监），其他人只许提议、不许直接改——多人改表是混乱之源。
- 术语争议解决：查行业惯例 → 查已出版译著 → 用户拍板。三步走完还定不了，标 `[待确认]` 继续翻，不许卡住全书进度。
- 交接：新译者加入时，第一件事是读 `glossary.md` + 跑一遍审计脚本，半小时内进入状态。

## 13. 附：术语表启动检查清单（开工 Day 1）

- [ ] `source/` 全文已通读（至少快速通读一遍）
- [ ] 四类术语候选清单已生成（含出现次数）
- [ ] 每个术语有 2-3 个译名候选 + 推荐理由
- [ ] 用户已拍板全部术语（`[待确认]` 单独成表）
- [ ] `glossary.md` 表头四列齐全，顶部有锁定状态与日期
- [ ] 缩写类术语备注列写明了首次出现规则
- [ ] 术语表已同步给所有协作者（云端/仓库，二选一且唯一）

## 14. 附：一句话速记

术语表 = 全书的"法律"。开译前立法（锁定），翻译中执法（审计），完稿后归档（随书出版）。谁改译名，谁负责全书统一替换——没有例外。
