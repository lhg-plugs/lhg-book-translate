# lhg-bt-audit：翻译一致性审计

> 目标：用机器的速度扫出低级错误，用人的判断守住翻译质量。
> 核心纪律：**blocker 清零才算过关**。审计不是挑刺，是交付前的最后一道门。

## 1. 何时使用

- 每译完一章想快速自查时 → 跑本 skill 第 3 步（只扫本章）
- 全书译完、准备交付前 → 跑完整流程（脚本 + 人工清单）
- 接手别人的译文做校对时 → 先跑脚本定位重灾区，再人工精读

## 2. 输入与输出

- **输入**：翻译项目目录（含 `glossary.md`、`source/`、`translated/`）
- **输出**：`docs/audit-YYYYMMDD.md` 审计报告，结论只能是"可交付"或"返工"，附返工优先级清单

## 3. 第一步：跑确定性脚本（必做）

```bash
python3 scripts/audit/translation_audit.py --target <项目目录> --format text
```

16 条规则分五类，脚本零第三方依赖、秒级出结果：

### 3.1 术语类（对照 glossary.md）
| 规则 | 级别 | 抓什么 |
|---|---|---|
| BT-TERM-001 | blocker | 术语原文残留在译文（如译文里还写着 machine learning） |
| BT-TERM-002 | warning | 用了术语表的"禁用译法"（如把 machine learning 写成"机械学习"） |
| BT-TERM-003 | nit | 术语表条目在译文中零引用（可能是漏译，也可能是术语表冗余） |

### 3.2 未译残留类
| 规则 | 级别 | 抓什么 |
|---|---|---|
| BT-UNTR-001 | warning | 连续英文单词片段残留（非术语表的英文，如整句忘了翻） |
| BT-UNTR-002 | warning | 大写缩写首次出现无中文对照（如裸奔的 GPU） |

### 3.3 标点类
| 规则 | 级别 | 抓什么 |
|---|---|---|
| BT-PUNC-001 | warning | 中文句子混用英文半角标点（, ; : ? ! 与句末英文句号） |
| BT-PUNC-002 | warning | 英文直引号 `"` 残留（应为弯引号 ""） |
| BT-PUNC-003 | nit | 中英文括号混用（中文旁用半角括号） |

### 3.4 结构类
| 规则 | 级别 | 抓什么 |
|---|---|---|
| BT-STRUCT-001 | blocker | 原文章节没有对应译文（缺译） |
| BT-STRUCT-002 | warning | 译文章节编号断层（如有第 1、3 章缺第 2 章） |
| BT-STRUCT-003 | warning | 标题数量与原文严重错位（标题丢了或多了） |
| BT-STRUCT-004 | warning | 译文文件没有对应原文（多译/错放） |

### 3.5 翻译腔类
| 规则 | 级别 | 抓什么 |
|---|---|---|
| BT-LIT-001 | warning | "的"字密度过高（欧化句式的第一信号） |
| BT-LIT-002 | warning | "进行"滥用（"进行分析"→"分析"） |
| BT-LIT-003 | warning | 被动句"被"高频（中文能主动就主动） |
| BT-LIT-004 | nit | 超长未断句（单句超长且无逗号断句） |
| BT-LIT-005 | nit | 程度副词堆砌（非常/十分/极其高频） |

阈值说明：脚本里的密度阈值是基于通用中文写作经验的启发值，不是语言学定论；不同文体（学术/小说）可按需调整，但**调阈值必须记录在审计报告里**，不许悄悄放水。

## 4. 第二步：人工评审清单（脚本抓不到的五件事）

1. **语气统一**：全书称谓一致吗（你/您）？口语书面体一致吗？抽每章开头两段读一遍，语气跳变的地方标出来。
2. **文化梗处理**：原文的双关、典故、幽默是怎么处理的？直译加注 / 意译替换 / 漏掉了——每种处理都要有交代，漏掉是事故。
3. **长难句质量**：从审计报告里挑 5 个最长的句子，大声读一遍——拗口就拆，不要信"我觉得还行"。
4. **数字与单位**：全书数字格式统一吗（阿拉伯/汉字）？单位统一吗（千米/km）？混用必须统一。
5. **抽样回译**：随机抽 3 段译文，遮住原文回译成原文语言，对照看意思走样了没有。走样就返工该段。

## 5. 第三步：输出审计报告

存为 `docs/audit-YYYYMMDD.md`，包含：扫描范围、blocker/warning/nit 数量、逐条返工清单（按优先级排序）、人工评审五项结论、最终结论（"可交付"或"返工"）。

豁免规则：warning 可以豁免，但必须在报告里写豁免理由；blocker 不许豁免。

## 6. 反模式（这些做法一定翻车）

- **只跑脚本不看人工项**：脚本能抓标点，抓不到"这段译文读起来像机翻"——人工五项是质量下限。
- **为清零改规则**：把"的"字阈值调高来让报告变绿，是作弊。阈值调整必须记录理由。
- **抽样走过场**：回译抽的都是短句简单的段落——专挑难的抽，简单的本来就不会错。
- **审计报告不存档**：口头说"改完了"等于没改，报告是交付物的一部分。
- **一章一审计嫌麻烦**：全书翻完再审计，返工量是按章审计的 5 倍以上。

## 7. 自检与反馈

质检门（审计流程自身的质检）：

- [ ] 脚本 16 条规则全跑完（summary 里 rules_run=16）
- [ ] blocker 数量为零（warning 豁免有书面理由）
- [ ] 人工五项每项都有书面结论（不是"还行"）
- [ ] 审计报告已存档到 `docs/`
- [ ] 返工后重跑脚本确认清零（改完不复查等于没改）

标准冒烟用例：`fixtures/trans-bad` 必须检出 blocker（含 BT-TERM-001 与 BT-STRUCT-001），`fixtures/trans-good` 必须零 blocker。

发现 bug 或有改进建议，以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-book-translate/issues，正文写清"复现步骤 → 实际表现 → 期望表现"。

## 8. 附：阈值调参指南

脚本里的翻译腔阈值是通用启发值，不同文体要调。调参三原则：

1. **先跑基线**：拿 3 章已出版的优秀译著（同文体）跑一遍脚本，记录它们的"的"字密度、"进行"频率——这就是你的文体基线。
2. **阈值 = 基线 × 1.3**：超过基线 30% 才报警，避免误报淹没有效信号。
3. **调参留痕**：任何阈值修改必须写进审计报告（改了哪条、从多少到多少、为什么），不许悄悄放水。

常见文体基线参考（每千字，仅供起步，务必用自己的语料校准）：
- 学术专著："的"约 55-70、"进行"约 3-5、"被"约 4-6
- 科普读物："的"约 45-60、"进行"约 1-3、"被"约 2-4
- 文学小说："的"约 40-55、"进行"约 0-1、"被"约 1-3


## 10. 附：高频误报与处理

- **BT-UNTR-001 误报**：代码块、URL、公式里的英文——脚本已自动排除围栏代码块；行内代码请用反引号包裹。
- **BT-PUNC-001 误报**：数字千分位逗号（如 1,000）——脚本排除数字内的半角逗号；小数点同理。
- **BT-LIT-001 误报**：法律/合同类文本"的"字天然偏高——按第 8 节调参，用文体基线校准。
